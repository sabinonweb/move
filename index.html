Variables & zero values

Declare a couple of variables in Go, and explain what a "zero value" is and why it matters that Go has no Option<T>.

var count int         // zero value: 0
var name string       // zero value: ""
var ready bool        // zero value: false
total := 0             // := infers int, only valid inside a function
count = 5               // no `mut` keyword needed — vars are mutable by default

Every Go type has a zero value it takes on when declared without an initializer, so "declared but not yet meaningfully set" compiles and runs instead of being a compile error. There's no Option<T> wrapping every maybe-absent value — the absence of a real value and the zero value look identical unless you check separately, which is exactly why map lookups return a second ok boolean, and why a nil pointer is a distinct, checkable state.

Rust anchorRust's let binding is immutable by default — mut is opt-in and compiler-enforced. Option<T> makes "no value" an explicit, matchable type most of the time.
Go answer
  • var works everywhere (including package scope) with an explicit or inferred type; := only works inside functions, always inferred.
  • No mut keyword — everything var/:=-declared is reassignable; only const is fixed, and only for compile-time constant expressions.
  • Zero values: numeric types → 0, string → "", bool → false, pointers/slices/maps/channels/funcs/interfaces → nil.
  • Why it matters: a struct with a forgotten field silently holds its zero value rather than failing to compile — a real source of Go bugs that Rust's Option/Default require you to be explicit about.

  • What's the difference between a nil slice and an empty (len 0) slice?
  • Why can you read from a nil map but not write to one?
Structs & methods

How do you attach a method to a type in Go, and when do you use a pointer receiver vs a value receiver?

type Counter struct { n int }

func (c Counter) Value() int { return c.n }     // value receiver — gets a copy
func (c *Counter) Inc()       { c.n++ }          // pointer receiver — mutates the original

A method is a function with a receiver argument before its name. A value receiver operates on a copy of the struct (mutations inside don't escape the method); a pointer receiver operates on the original, so it's the only way to mutate state or avoid copying a large struct on every call.

Rust anchorMaps to impl Counter { fn value(&self) -> i32 {...} fn inc(&mut self) {...} } — &self ≈ value receiver, &mut self ≈ pointer receiver.
Go answer
  • No impl block — methods are free functions with a receiver clause, and can live in any file in the same package.
  • Mixing receiver types on the same type is legal but bad practice — once any method needs to mutate, use pointer receivers consistently for that type.
  • Unlike Rust, a value receiver's copy isn't checked against concurrent mutation — no borrow checker means two goroutines can race on the same struct's fields with no compile-time warning.

Likely follow-ups

  • If Counter held a big slice, what's the cost of a value receiver by mistake?
  • Can an interface be satisfied by a pointer-receiver-only type if you only have a value in hand?
Slices, arrays & maps

What's the actual structure of a Go slice under the hood, and what happens when you append past capacity?

arr := [3]int{1, 2, 3}      // fixed-size array — length is part of the type
s := []int{1, 2, 3}          // slice: a view over an underlying array
s = append(s, 4)              // may reallocate if len == cap
m := map[string]int{}         // map, reference type like a slice

A slice is a small struct of (pointer, length, capacity) pointing at an underlying array — slicing an existing slice/array shares that memory rather than copying it, so mutating through one slice can be visible through another. append grows in place only while there's spare capacity; once it runs out, Go allocates a new, larger backing array and copies everything over, silently detaching the slice from whatever it used to share memory with.

Rust anchorA Go slice is structurally close to &mut [T] (a fat pointer: ptr+len) but growable like Vec<T> — Go collapses "borrowed view" and "owned growable buffer" into one type, which Rust deliberately keeps separate and enforces with the borrow checker.
Go answer
  • Arrays are value types (copied on assignment; [3]int and [4]int are different types); slices are reference-like (assignment copies the header, not the backing array).
  • Two slices from the same array can alias — write through one, see it through the other, until an append reallocates one of them.
  • Maps are reference types too; a nil map is readable (zero value + ok=false) but panics on write, unlike a nil slice which is safely appendable.

Likely follow-ups

  • Two slices share an underlying array — you append to one. Does the other see the change?
  • Why does Go make you pass a map by value into a function, yet mutations are still visible to the caller?
Control flow

Go has one loop keyword. What does for cover that Rust splits into for, while, and loop?

for i := 0; i < 10; i++ { }   // classic C-style for
for cond { }                    // while-style
for { }                          // infinite loop
for i, v := range items { }     // range-based iteration

All four forms are the same for keyword with different clauses omitted. There's no while, no loop, no ternary operator, and no parentheses around conditions — but braces are mandatory even for a single-statement body, ruling out a whole class of dangling-else bugs.

Rust anchorRust's for x in iter, while cond, and loop { } are three keywords for three of these same cases; Go picked one keyword and lets you drop clauses instead.
Go answer
  • for range over a slice gives (index, value); over a map gives (key, value) in randomized order — Go deliberately randomizes map iteration to stop anyone relying on it.
  • break/continue support labels for jumping out of nested loops.
  • switch doesn't fall through by default (opposite of C) — needs an explicit fallthrough, and cases can be non-constant expressions.

Likely follow-ups

  • How would you break out of two nested loops at once in Go?
  • What happens if you modify a map while range-ing over it?
Pointers, no borrow checker

Go has pointers, & and *. What safety does Rust's borrow checker give you that Go's garbage collector doesn't?

func inc(n *int) { *n++ }
x := 5
inc(&x)   // x is now 6 — pointer lets the function mutate the caller's variable

Go pointers work like C's, minus pointer arithmetic. Because Go is garbage collected, there's no use-after-free or dangling pointer risk — the runtime keeps anything still reachable through a pointer alive. What it doesn't give you is compile-time aliasing safety: nothing stops two goroutines from holding a pointer to the same value and mutating it concurrently with no warning.

Rust anchorRust's borrow checker enforces, at compile time, that a value has either one mutable reference or many immutable ones, never both. Go has no equivalent — the same aliasing pattern that's a compile error in Rust is just normal Go code, and a possible data race the -race detector might catch at runtime, if you run it.
Go answer
  • No lifetimes — Go doesn't need them because the GC keeps referenced memory alive regardless of how many pointers point at it or for how long.
  • Escape analysis decides stack vs heap automatically — no Box::new equivalent; the compiler infers it from whether a pointer to the value escapes the function.
  • The real safety gap: concurrent mutation through shared pointers is legal and silent — exactly why go build -race and disciplined mutex/channel use matter so much, where Rust would have refused to compile the unsafe pattern.

Likely follow-ups

  • When does the Go compiler put a local variable on the heap instead of the stack, and how would you check?
  • Given no borrow checker, how do you personally guard against a data race in review?
Multiple returns & error idiom

Go doesn't have tuples generally, but functions return multiple values natively. How does that shape day-to-day error handling?

func divide(a, b int) (int, error) {
    if b == 0 {
        return 0, errors.New("divide by zero")
    }
    return a / b, nil
}

result, err := divide(10, 0)
if err != nil {
    // handle it
}

Multiple return values are a language feature, not a tuple/struct trick — (int, error) is a real two-value return, and the (value, error) pairing is pure convention, not something the compiler enforces the way Result<T,E> does. The zero value of the first return is what gets returned alongside a non-nil error, by convention — callers are expected to ignore it whenever err != nil.

Rust anchorCompare to the Error Handling card in Fundamentals — Result<T,E> bundles success/failure into one enum the compiler forces you to handle; Go's (T, error) is two independent values with no such enforcement.
Go answer
  • Multiple return is used outside error handling too — map lookups (v, ok := m[k]), type assertions (v, ok := x.(string)).
  • Named return values let you declare the return variables in the signature and just return bare — useful with defer for adjusting an error right before the function exits.
  • Same convention-not-enforcement gap as the Fundamentals Error Handling card — worth connecting the two in an interview answer.

Likely follow-ups

  • What's a named return value, and why might defer want one?
Packages & visibility

How does Go decide what's public vs private, and what's the Go equivalent of Cargo.toml / a crate?

// go.mod
module github.com/you/project
go 1.22

// file: user.go, package "models"
type User struct {
    Name string   // exported — capitalized
    email string  // unexported — lowercase, package-private
}

Visibility is decided purely by capitalization — no pub keyword. An identifier starting with an uppercase letter is exported and visible outside its package; lowercase stays private to the package. A package is just "the set of .go files in one directory declaring the same package name" — there's no nested module tree like Rust's mod a::b::c; you get one flat namespace per directory, and depth comes from directory structure instead.

Rust anchorgo.mod + go.sum ≈ Cargo.toml + Cargo.lock. Rust's pub/pub(crate) visibility keywords become Go's capitalization convention — there's no equivalent of pub(crate)'s in-between visibility; it's exported-everywhere or private-to-the-package, full stop.
Go answer
  • go.mod declares the module path (also the import path prefix) and Go version; go.sum pins dependency checksums, playing the Cargo.lock role.
  • A directory is a package; import "github.com/you/project/models" pulls in everything exported from that directory's package.
  • No sub-module privacy tier: if related packages need to share unexported internals, the convention is an internal/ directory, which the compiler specially restricts to importers within the same module tree.

  • Where would you put code several of your own packages need, that external importers shouldn't be able to use?

Goroutines & the scheduler

You mentioned Go's M:N threading model in a mock interview but couldn't go deeper than the name. Explain the GMP model precisely — what are G, M, and P, and how does a goroutine actually get onto a CPU?

func worker(id int) { fmt.Println("worker", id) }

for i := 0; i < 5; i++ {
    go worker(i)   // launches a goroutine — returns immediately, doesn't block
}

Go's concurrency model is built on three moving pieces the runtime juggles for you: G (goroutine — a lightweight, user-space unit of work with a tiny growable stack), M (machine — a real OS thread the kernel schedules), and P (processor — a logical execution context, one per GOMAXPROCS, that an M must hold to run Go code). A goroutine doesn't map to a thread 1:1; many G's queue up on each P, and the scheduler hands them to whichever M is free, work-stealing from other P's queues when its own runs dry. That's what "M:N" means — M goroutines multiplexed onto N OS threads. Since Go 1.14, the runtime can even interrupt a goroutine mid-loop via a signal if it's hogging a P too long, so one runaway goroutine can't starve the rest.

Rust anchorTokio's multi-thread runtime is also M:N: many tasks scheduled onto a fixed pool of worker OS threads (default = num_cpus), each with its own local work-stealing run queue. Structurally this is very close to Go — the real differences are elsewhere.
Go answer
  • G = goroutine: the unit of work, a function plus a small (~2KB, growable/copyable) stack.
  • M = machine: an actual OS thread.
  • P = processor: a logical context, count set by GOMAXPROCS. A P holds a local run queue of G's and must be held by an M to execute Go code.
  • The scheduler multiplexes G's onto P's onto M's; idle P's steal work from busy P's local queues (and a global queue) so no core sits idle while another has a backlog.
  • Key divergence from Tokio: since Go 1.14, the runtime can asynchronously preempt a goroutine that's been running too long (signal-based, checked at function-call/loop safepoints), so a CPU-bound goroutine can't starve the scheduler. Tokio has no equivalent — a tight loop without an .await point blocks its worker thread outright.

Likely follow-ups

  • What happens if you set GOMAXPROCS=1 — do goroutines still run concurrently?
  • Why can a goroutine block an OS thread anyway (e.g. a blocking syscall), and how does the runtime cope?
Channels & select

Compare Go's buffered vs unbuffered channels and the select statement to what you'd reach for in Tokio.

ch := make(chan int)         // unbuffered
buffered := make(chan int, 3) // buffered, capacity 3

go func() { ch <- 42 }()      // blocks until someone receives
v := <-ch                      // receives 42

select {
case v := <-ch:
    fmt.Println(v)
default:
    fmt.Println("nothing ready")
}

A channel is Go's built-in typed pipe between goroutines. Unbuffered channels have zero capacity — a send blocks until some goroutine is ready to receive at that exact moment, making it a synchronization point as much as a data transfer. Buffered channels (make(chan T, n)) hold up to n values before a send blocks, letting producer and consumer run at different paces. select lets a goroutine wait on multiple channel operations at once and proceeds with whichever becomes ready first — with a default case, it becomes non-blocking. The Go proverb behind all of it: "don't communicate by sharing memory, share memory by communicating."

Rust anchortokio::sync::mpsc (bounded ≈ buffered, unbounded ≈ "infinite buffer"), oneshot for a single value, and tokio::select! for multiplexing several async ops with an optional else.
Go answer
  • Unbuffered chan: send blocks until a receiver is ready — a synchronous rendezvous, not a queue.
  • Buffered chan T, n: send only blocks once the buffer of size n is full — decouples producer/consumer pace up to that limit.
  • select picks whichever ready case fires first among several channel ops, at random if multiple are ready; a default case makes it non-blocking, like Tokio's select! with a fallback branch.
  • Divergence: Go channels are native multi-producer multi-consumer — mpsc is single-consumer by name, so fan-out needs a broadcast/watch channel. And closing a Go channel broadcasts to every receiver (reads drain then return the zero value with ok=false) — there's no built-in Rust equivalent to "close."

Likely follow-ups

  • What happens if you send on a closed channel? Receive from one?
  • Why would you deliberately use a nil channel in a select statement?
sync primitives

sync.Mutex, sync.WaitGroup, and the sync/atomic package — what do they buy you, and what's the sharpest difference from the Rust equivalents?

var mu sync.Mutex
var count int

mu.Lock()
count++            // nothing forces this — on you to lock before touching count
mu.Unlock()

var wg sync.WaitGroup
wg.Add(1)
go func() { defer wg.Done(); doWork() }()
wg.Wait()

sync.Mutex is a bare lock: call .Lock() before touching shared data and .Unlock() when done, but the compiler enforces none of it — the "protected" data is just a regular field sitting next to the mutex by convention. sync.WaitGroup lets one goroutine wait for a set of others to finish: Add(n) before launching them, each calls Done() when finished, Wait() blocks until the counter hits zero. sync/atomic gives lock-free primitives (atomic.Int64, compare-and-swap) for simple counters or flags where a full mutex would be overkill.

Rust anchorMutex<T> wraps the data — you cannot touch T without going through .lock(), so the borrow checker makes "forgot to lock" a compile error, not a runtime bug.
Go answer
  • sync.Mutex protects nothing by the type system — it's a bare lock, and it's on you to remember which fields it guards and to always lock before touching them. This is the single biggest DX gap vs Rust's Mutex<T>, and worth saying explicitly.
  • sync.WaitGroup: Add/Done/Wait to block until a set of goroutines finish — roughly collecting a Vec<JoinHandle> and joining them all, or tokio::join! for a fixed set.
  • sync/atomic (atomic.Int64 etc.) maps directly to std::sync::atomic::AtomicI64 — same lock-free CAS-based primitives underneath.

Likely follow-ups

  • How would you catch a "forgot to lock" bug in Go, given the compiler won't?
  • When would you reach for a channel instead of a mutex to protect shared state?
Error handling

Go has no Result<T,E> — errors are just values. Explain errors.Is vs errors.As and how %w wrapping works, and name the one safety property Go gives up here that Rust doesn't.

_, err := os.Open("config.yaml")
if err != nil {
    wrapped := fmt.Errorf("loading config: %w", err)
    if errors.Is(wrapped, os.ErrNotExist) {
        // handle missing file specifically
    }
}

In Go, an error is any value satisfying interface{ Error() string } — there's no special language support, no exceptions. The convention is a function returns (result, error) and the caller checks if err != nil. fmt.Errorf("context: %w", err) wraps an error while keeping the original accessible in a chain. errors.Is(err, target) asks "does this chain contain that specific sentinel error" (e.g. sql.ErrNoRows). errors.As(err, &target) asks "does this chain contain an error of this concrete type," and if so assigns it into target so you can read its fields.

Rust anchorResult<T,E> is #[must_use] — the compiler nags if you drop it silently. ? propagates and uses From<E> to convert at the boundary, which is effectively automatic wrapping; anyhow::Context is the manual version of Go's %w.
Go answer
  • fmt.Errorf("doing x: %w", err) wraps err, preserving it in a chain rather than stringifying it away.
  • errors.Is(err, sentinel) walks the chain checking equality (or an Is method) against a known sentinel value — "is this that specific error, however deep it's wrapped."
  • errors.As(err, &target) walks the chain looking for the first error assignable to target's concrete type — "give me the typed error out of this chain."
  • The safety Go gives up: nothing forces you to check err. if err != nil is convention, not compiler-enforced — an ignored error compiles clean. Rust's Result makes that a type-level obligation.

  • How would a linter catch an ignored error in a Go codebase, since the compiler won't?
  • When would you deliberately use a sentinel error vs a typed error struct?
Interfaces vs traits

How does a Go type satisfy an interface, and how is that fundamentally different from implementing a Rust trait?

type Stringer interface { String() string }

type Point struct{ X, Y int }
func (p Point) String() string { return fmt.Sprintf("(%d,%d)", p.X, p.Y) }
// Point satisfies Stringer automatically — no "impl Stringer for Point" anywhere

A Go interface is a set of method signatures. Any type that happens to implement all of them satisfies the interface automatically — there's no impl InterfaceName for Type anywhere; the compiler just checks the method set matches wherever the interface is used. This is structural typing (sometimes called "duck typing, but statically checked"): you can define a two-line interface in your own package and pass in a struct from a totally unrelated library, as long as its methods line up — and a type can satisfy interfaces its author never even knew existed.

Rust anchorA trait must be explicitly implemented (impl Trait for Type), checked against coherence/orphan rules, and can carry default methods and generic bounds resolved at compile time (static dispatch) or via dyn Trait (dynamic dispatch).
Go answer
  • Go interface satisfaction is implicit / structural: a type satisfies an interface just by having the right method set — no implements keyword, no declaration anywhere near the type or the interface.
  • This means you can define an interface after the fact, in a consuming package, for a type you don't own — a pattern Rust's orphan rule explicitly blocks.
  • Trade-off: it's easy to satisfy an interface by accident (wrong method, right signature), and there's no compiler prompt telling you which interfaces a type does or doesn't implement — you find out at the call site.
  • Dynamic dispatch is the default via an interface value (a type+pointer pair); Go's generics (1.18+) added compile-time-checked type parameters, but interfaces remain the primary polymorphism tool, unlike Rust where trait bounds are more idiomatic than trait objects.

Likely follow-ups

  • How do you discover, in a large Go codebase, which interfaces a struct satisfies?
  • When would you reach for Go generics instead of an interface?
Struct embedding

Go doesn't have inheritance, but it has struct embedding. What does embedding actually do, and where does the "not inheritance" distinction bite you?

type Base struct{}
func (Base) Greet() string { return "hi from Base" }

type Outer struct { Base }   // embedded, unnamed field

o := Outer{}
o.Greet()   // "hi from Base" — promoted from Base

Struct embedding nests one struct (or interface) inside another without naming the field, e.g. type Server struct { *log.Logger }. Go "promotes" the embedded type's methods and fields up to the outer struct, so server.Println(...) works even though Println is defined on *log.Logger. It looks like inheritance but is really automatic delegation — there's no dynamic dispatch. If Server defines its own Println, it simply shadows the embedded one; calls from inside the embedded type's own methods still go to the embedded type's version, never the outer "override."

Rust anchorRust has no embedding sugar — composition is explicit: a field plus manual delegation, or leaning on Deref for smart-pointer ergonomics (and that's considered a footgun when abused for non-pointer types).
Go answer
  • Embedding a struct (or interface) as an unnamed field promotes its fields and methods to the outer type — you can call outer.Method() even though Method is defined on the embedded type.
  • It's syntactic delegation, not polymorphism: there's no virtual dispatch. If the outer type defines a method with the same name, it shadows the embedded one statically — the embedded type's own methods never call the outer's overrides (no "override" concept at all).
  • Where it bites: people reach for embedding expecting OOP-style "is-a" inheritance and get surprised that an embedded interface's method calling another method on itself won't pick up the outer type's version.

Likely follow-ups

  • Give an example where embedding is the right tool vs where plain composition would be clearer.

PUT vs PATCH

Define PUT vs PATCH precisely — including the idempotency claim people usually get wrong about PATCH.

PUT /users/5
{ "name": "Sabin", "email": "s@x.com" }   // full resource — omit email, it's cleared

PATCH /users/5
{ "email": "new@x.com" }                    // only this field changes

REST's HTTP verbs each carry a contract beyond "this action happens." PUT means: here is the complete, final state of this resource — store exactly this. PATCH means: here is a set of changes — apply them to whatever the resource currently is. That distinction is why PUT is idempotent by definition (replacing with the same full state twice is a no-op the second time), while PATCH's idempotency depends entirely on what the patch operation says: "set field to X" is idempotent, "append to array" or "increment" is not.

Model answer
  • PUT replaces the entire resource at a known URI with the full representation you send. It's guaranteed idempotent by spec — sending the same PUT N times leaves the server in the same state as sending it once. A field you omit from the body is semantically cleared, because it's a full replace.
  • PATCH applies a partial modification — the body is a description of a change (a JSON Merge Patch or JSON Patch document), not a full resource. PATCH is not guaranteed idempotent by spec (RFC 5789) — "set status to active" happens to be idempotent, but "increment view count by 1" is a valid PATCH and clearly isn't.
  • The trap: saying "PATCH is idempotent" as a blanket rule. It depends on the semantics of the specific patch operation.

Likely follow-ups

  • Your PATCH endpoint takes a full JSON body of just the changed fields — is that JSON Merge Patch or JSON Patch, and what's the difference?
  • Would you ever implement PATCH as idempotent on purpose, even if the spec doesn't require it? Why?
Status codes

When do you return 200 vs 201 vs 204? And 400 vs 422? And 401 vs 403?

POST /users              -> 201 Created, Location: /users/42
GET  /users/42            -> 200 OK
DELETE /users/42          -> 204 No Content
POST /users (bad json)    -> 400 Bad Request
POST /users (email taken) -> 422 Unprocessable Entity

HTTP status codes fall into families: 2xx means success (with sub-distinctions for what kind of success — created vs. no body vs. accepted-but-async), 4xx means the client did something wrong (malformed, not authenticated, not permitted, not found, conflicting state), 5xx means the server broke. The skill isn't memorizing every code — it's picking the one whose stated meaning genuinely matches the situation. A 404 for "you're not allowed to see this" hides whether the resource exists at all from an unauthorized caller, which is sometimes exactly the point and sometimes a bug that breaks legitimate error messages.

Model answer
  • 200 OK: successful request with a response body (GET, or a PUT/PATCH that returns the updated resource).
  • 201 Created: POST that created a new resource — include a Location header pointing at it.
  • 204 No Content: succeeded, nothing to return (a DELETE, or a PUT/PATCH you don't echo back).
  • 400 Bad Request: the request is malformed — bad JSON, wrong types, missing required structure. 422 Unprocessable Entity: well-formed and parseable, but semantically invalid — fails a business rule or validation check. (Some APIs collapse both into 400; know the distinction exists and be able to defend either choice.)
  • 401 Unauthorized: really means unauthenticated — no or invalid credentials. 403 Forbidden: authenticated, but not permitted to do this.

Likely follow-ups

  • A user hits an endpoint for a resource that exists but isn't theirs — 403 or 404? Defend it.
Resource naming & versioning

What makes a URL scheme "RESTful" in terms of naming, and how would you version an API?

GET /v1/users/42/orders     // nested — orders genuinely belong to a user
GET /v1/orders?userId=42    // flatten instead, once nesting gets deep

REST resource design treats a URL as a noun identifying a thing, and the HTTP method as the verb acting on it. A collection is plural (/users); a specific member is the collection plus an identifier (/users/42); a sub-resource nests only when it's genuinely owned by the parent and doesn't make sense standalone (/users/42/orders). Versioning exists because a breaking change to a resource's shape can't just silently ship — either the URL declares the version, or the client negotiates it via a header. Both are legitimate as long as the team is consistent and has an actual deprecation policy.

Model answer
  • Nouns, not verbs — the HTTP method is the verb. /getUser is wrong; GET /users/{id} is right.
  • Plural collection names (/users, not /user), nested only as deep as ownership genuinely goes (/users/{id}/orders is fine; five levels deep usually means you should flatten with a query param instead).
  • Versioning: URL-prefix (/v1/users) is simple, cacheable, and debuggable by eye but pollutes the URL and implies the resource itself changed. Header-based (Accept: application/vnd.api+json;version=1) keeps URLs clean but is harder to explore/curl and easy to forget. Most teams pick URL-prefix for the ergonomics and accept the "impurity."

Likely follow-ups

  • How do you deprecate v1 once v2 ships without breaking existing clients overnight?
Pagination

Offset/limit pagination vs cursor-based — what breaks with offset/limit at scale?

GET /items?offset=2000&limit=20        // offset/limit: slow + driftable at depth
GET /items?after=item_1999&limit=20    // cursor: stable, indexed lookup

Any pagination scheme answers "given this page, how do I get the next one." Offset/limit answers with a row count to skip — trivial to implement, but the database still has to scan past offset rows to find where to start, and if a row is inserted or deleted while you're paging, your window drifts and you can see a duplicate or skip an item. Cursor (keyset) pagination instead answers with "the last thing you saw" — usually an indexed column's value — and asks for rows after that. It's stable under concurrent writes and its cost doesn't grow with depth, at the cost of losing random access to an arbitrary page number.

Model answer
  • Offset/limit: simple to implement and to jump to an arbitrary page, but (a) the DB still has to scan and discard the first offset rows, so it gets slower as offset grows, and (b) it drifts under concurrent writes — insert a row before page 2 loads and you'll see a duplicate or skip an item.
  • Cursor / keyset pagination: page by "give me rows after this sort key," using an indexed column as the cursor. Stable under concurrent writes, and query cost doesn't grow with page depth — but you lose the ability to jump straight to page 40.

Likely follow-ups

  • How do you paginate a feed sorted by a non-unique column (e.g. created_at with ties)?
Error response shape

What does a well-designed error response body look like, and why?

{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "email is already in use",
    "fields": ["email"]
  }
}

An API's error responses are part of its contract just as much as its success responses — a client needs to parse and branch on them programmatically, not just display them. The core idea is separating a stable, machine-readable code a client can switch on from a human-readable message that can change wording freely without breaking anyone's integration. Consistency matters more than any specific shape: every endpoint should return errors in the same envelope, or client code ends up special-casing each one.

Model answer
  • A consistent envelope across every endpoint, e.g. {"error":{"code":"VALIDATION_FAILED","message":"...","fields":[...]}}.
  • A machine-readable code the client can branch on programmatically, separate from a human-readable message meant for logs/display — don't make clients string-match the message.
  • Never leak internals: no stack traces, no raw DB error text, no SQL fragments in the response body.

Databases · Caching · Scaling

Scale StuddyBuddy's anonymous peer-matching to 100k concurrent users. Where does it break first, and what do you change?

Dimensions a strong answer touches
  • App servers stateless behind a load balancer — matching state can't live in one instance's memory, or users on different instances never match.
  • Move the matching queue/criteria into a shared store (Redis) so any instance can pair any two waiting users.
  • DB read scaling (indexes, read replicas) once match history/lookups grow.
  • WebSocket/chat fan-out at 100k connections: sticky sessions or a pub/sub broker so a message reaches a user regardless of which instance holds their socket.
  • Backpressure when demand for a subject outstrips supply of matchable peers — a queue with a visible wait state, not a silent hang.
Fault Tolerance

Design DAI's task distribution to tolerate Byzantine/faulty nodes. Sketch the approach and the failure modes you're designing against.

Dimensions a strong answer touches
  • Redundant execution across N nodes + comparing results (majority vote / consensus) rather than trusting a single node.
  • A reputation or stake-weighted trust score that shifts over time, not a flat "trust everyone equally."
  • Three distinct failure modes handled differently: crash (node just disappears — timeout + retry), Byzantine (node returns a plausible-looking wrong answer — needs the redundancy/vote), and slow-but-honest (needs a timeout that doesn't unfairly penalize it).
  • The cost trade-off: redundancy factor directly multiplies compute cost, so it should track how much you actually distrust the network, not be a fixed constant.

Concurrency in Go

MediVault needs to stay reliable when nodeMCU devices drop connection. If you rebuilt the device-handling layer in Go, how would goroutines and channels model this?

Dimensions a strong answer touches
  • One goroutine per device connection is cheap precisely because of the M:N scheduler (fundamentals section) — thousands of lightweight goroutines, not thousands of OS threads.
  • A heartbeat via time.Ticker combined with select against a timeout channel to detect a drop, instead of waiting on a blocking read forever.
  • A fan-in pattern: each device goroutine writes events onto one shared channel, a single goroutine consumes and processes in order.
  • Backpressure: a bounded channel with an explicit drop-oldest or block policy if the processing side falls behind — an unbounded channel just hides the problem until memory blows up.
  • Clean shutdown on disconnect via context.Context cancellation, so a dropped device doesn't leak its goroutine forever.
